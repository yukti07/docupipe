# Component Inventory

The canonical list of every UI component in Quarry, so that building a screen means *assembling*
rather than inventing.

Companion to [`screen-inventory.md`](screen-inventory.md) (what screens exist) and
[`ui-design-spec.md`](ui-design-spec.md) (what things look like).

---

## The rule

> **Reuse existing components wherever possible. Do not create a new component if an existing one
> can satisfy the requirement.**

Before writing any new component:

```
Need a piece of UI
      ↓
Is it in this inventory?
 ├── Yes → use it. If it's close but not exact, add a variant to it
 └── No
      ↓
 Can a shadcn/ui primitive do it?
 ├── Yes → install the primitive, don't hand-write one
 └── No
      ↓
 Can it be composed from two or three things already here?
 ├── Yes → compose in place. Only extract a component when it appears a third time
 └── No
      ↓
 Build it — and add it to this file in the same change
```

**The third-use rule.** Two similar bits of markup on two screens is a coincidence. Three is a
component. Extracting on the first sighting produces abstractions shaped by one caller, which then
fight the second one.

## Layers

| Layer | What it is | Who writes it | Lives in |
|---|---|---|---|
| **1 · Primitives** | shadcn/ui components | Generated by the CLI — **never hand-edited** | `src/components/ui/` |
| **2 · Common** | Generic pieces built from primitives. Nothing here knows what a document is | Us | `src/components/common/` |
| **3 · Domain** | Quarry-specific. These know about cells, evidence, schemas, batches, failures | Us | `src/components/quarry/` |

A layer only ever depends downward. Domain uses common uses primitives. Never the reverse.

---

## Layer 1 · Primitives

Install with `npx shadcn@latest add <name>`. If one of these is missing, install it rather than
writing your own.

| Component | Used for |
|---|---|
| `button` | Everywhere |
| `input` · `label` | Adding a field, settings |
| `select` · `dropdown-menu` | **Field type**, download format, density, row actions |
| `dialog` | Download all, Merge picker, destructive confirmation — **and nothing else** |
| `sheet` | Schema and evidence panels below 1024px |
| `resizable` | The list / panel split on S02 and S04 |
| `tabs` | Processing ↔ Machine view; tables within a multi-table file |
| `tooltip` | Supplementary hints only — never the sole carrier of a disabled reason |
| `badge` | Base for `StatusBadge` |
| `progress` | Base for upload and batch progress |
| `separator` · `scroll-area` | Layout |
| `skeleton` | Table and panel loading |
| `sonner` | Toasts — confirmations only, never errors |
| `popover` | Apply-to-all file list, filter menus |
| `checkbox` · `switch` | Merge selection, settings, row selection |
| `alert` | Base for `PausedBanner` and inline failures |

`select` is load-bearing here in a way it wasn't before: the field-type control is the **only**
editable thing on a schema field row, so it carries the entire schema-editing interaction.

## Layer 2 · Common

Generic, reusable, and deliberately ignorant of the product's domain.

| ID | Component | Purpose | Variants / states | Screens |
|---|---|---|---|---|
| C01 | **`StatusBadge`** | The one badge in the app | `success` · `review` · `error` · `paused` · `neutral` | S01 S02 S04 S06 S09 |
| C02 | **`EmptyState`** | Nothing here yet | With or without an action | S01 S06 S09 S10 |
| C03 | **`ErrorState`** | Something failed at page level | With retry, with back | S01 S06 S14 S15 |
| C04 | **`LoadingState`** | Waiting, with words | `determinate` (has a fraction) · `labelled` (doesn't) | S01 S03 S04 S06 S07 S10 |
| C05 | **`PageHeader`** | Title, subtitle, actions | Compact and full | S01 S02 S03 S12 |
| C06 | **`Toolbar`** | Row of controls above content | — | S06 |
| C07 | **`GatedButton`** | **A button that explains why it's disabled** | `enabled` · `disabled-with-reason` | S02 S09 S10 |
| C08 | **`KeyHint`** | Shows a keyboard key — `Esc`, `Enter` | Single key, key sequence | S03 S11 |
| C09 | **`ConfirmDialog`** | Confirm something costly | `default` · `destructive` | S06 S12 |
| C10 | **`SplitPane`** | List on the left, detail panel on the right | `closed` · `open` · resizable · sheet below 1024px | S02 S04 S06 |

**`LoadingState` exists to make the no-bare-spinner rule structural.** If loading always goes
through a component that requires a label, it becomes impossible to ship a wordless spinner by
accident.

**`GatedButton` does the same job for disabled controls.** The product has four gated actions
(Preview / Edit, Review schemas, Convert, Merge), and a disabled button with no explanation is the
fastest way to make a considered product feel broken. The component **requires** a reason string
whenever it is disabled, and puts that reason in the accessible name as well as on screen — so the
rule holds for screen readers too, which is where it matters most.

**`SplitPane` is one component used by both split screens**, which is what makes the schema panel
and the evidence panel behave identically. Learn it once, know it everywhere.

## Layer 3 · Domain

These know about Quarry.

### Upload — S02

| ID | Component | Purpose | States |
|---|---|---|---|
| D01 | **`DropZone`** | Drag target and file picker in one | `idle` · `dragging` · `dragging-invalid` · `disabled`. States the accepted formats and size cap inside itself |
| D02 | **`FileRow`** | One file and everything about it | `staged` · `checking` · `rejected` · `uploading` · `failed` · `uploaded` · `reading-shape` · `shape-ready` · `no-shape` · `unreadable`. Owns its own retry |
| D03 | **`FileList`** | The list of `FileRow`s, plus the summary | — |
| D04 | **`ConvertBar`** | The footer: Review schemas, Convert, and their reasons | `blocked` · `ready` · `converting` |

**`FileRow` is used on two screens with different trailing controls** — Preview / Edit on S02, View
and Download on S04. One component with a trailing slot, not two components. Building it twice is
how the two screens drift apart.

### Schema — S03

| ID | Component | Purpose | States |
|---|---|---|---|
| D05 | **`SchemaEditor`** | One file's schema — the panel and the all-files card are the same thing at two widths | `reading` · `ready` · `editing` · `invalid` · `saving` · `saved` · `save-failed` · `no-shape` |
| D06 | **`SchemaFieldRow`** | One field: name (read-only) and type (editable) | `detected` · `type-changed` · `added-by-you` · `invalid` |
| D07 | **`FieldTypeSelect`** | The type control — the only editable thing on a field | `text` · `number` · `date` · `currency` · `boolean` · `list` |
| D08 | **`AddFieldControl`** | Inline name + type for a field the user adds | `idle` · `open` · `invalid` |
| D09 | **`ApplyToAllControl`** | Propagate this schema, with the count in its label | `unavailable` · `offered` · `confirming` · `applied` |
| D10 | **`SchemaCard`** | One schema in the all-files view and the merge picker | `ready` · `edited` · `shared-with-n` · `failed` |
| D11 | **`SchemaGroupList`** | Schemas grouped by identical shape, with counts | — |

**`SchemaFieldRow` must render the field name as plainly non-editable** — mono, no input chrome, no
hover affordance. A greyed-out rename control would be worse than nothing: an affordance that never
works reads as a bug, and this one would read as a bug on every row of every schema.

**`ApplyToAllControl` carries its count in its label** (*"Apply to all · 12 files"*), because that
count is the entire value of the feature. It never applies straight from the button — pressing it
reveals the affected file names first.

### Processing — S04, S05

| ID | Component | Purpose | States |
|---|---|---|---|
| D12 | **`StatusSentence`** | The one honest line in the header | `reading-shapes` · `running` · `paused` · `finished` · `failed` |
| D13 | **`PausedBanner`** | Waiting on a limit, with the resume time | `quota` · `user-cap` |
| D14 | **`StageColumn`** | One processing stage with its documents (P1) | `idle` · `active` |
| D15 | **`ProviderChainStrip`** | The provider chain, one link greyed (P1) | `live` · `spent` · `unavailable` |

Per-file status on S04 is `FileRow` (D02), not a separate component.

### Tables — S01, S06

| ID | Component | Purpose | States |
|---|---|---|---|
| D16 | **`DataTable`** | The TanStack wrapper — sort, filter, virtualize, density | `loading` · `loaded` · `empty` · `filtered-empty` |
| D17 | **`DataCell`** | **The most important component in the app** | `value` · `not-found` · `marked` · `failed-row` · `corrected` (P2) |
| D18 | **`MarkedCellReason`** | Why this cell is amber, inline in the table | One per verification rule |
| D19 | **`BatchCard`** | A batch on the workspace | `awaiting-schemas` · `converting` · `paused` · `finished` · `finished-with-failures` · `failed` |
| D20 | **`DensityToggle`** | Comfortable ↔ compact | — |

**`DataCell` renders a merged table's rows unchanged.** A merged table is a `DataTable` with one
extra source-file column, not a new component — which is what keeps evidence working across the
merge for free.

### Evidence — S07

| ID | Component | Purpose | States |
|---|---|---|---|
| D21 | **`EvidencePanel`** | The shell — header, source name, close. Read-only | `closed` · `opening` · `open` · `loading` · `unavailable` |
| D22 | **`EvidenceView`** | Dispatches on locator type to the right view below | — |
| D23 | **`EvidencePageView`** | pdf.js page render + highlight — PDF, scan, image | `rendering` · `rendered` |
| D24 | **`EvidenceAudioView`** | Player cued to the moment, with the words | `loading` · `ready` · `playing` |
| D25 | **`EvidenceTextView`** | Paragraph with the phrase highlighted | — |
| D26 | **`EvidenceRecordView`** | Sheet, row and column | — |
| D27 | **`EvidenceUnavailable`** | This format can't report a position — say so, show the text | — |
| D28 | **`HighlightBox`** | The box itself, and the drawing animation | `drawing` · `drawn` · `editable` (P2, for correcting by box) |

**One interface, five views.** Every adapter produces the same kind of locator, so `EvidenceView`
switches on its type and nothing above it needs to know which format it's looking at. Adding a
format later means adding one view, not touching the panel.

### Download — S08

| ID | Component | Purpose | States |
|---|---|---|---|
| D29 | **`DownloadFileButton`** | One file's table, one click, no dialog | `idle` · `preparing` · `failed` |
| D30 | **`DownloadAllDialog`** | Format choice and the honest counts | `idle` · `warning` · `preparing` · `done` · `failed` · `nothing-to-download` |

The asymmetry is deliberate and must survive refactoring: per-file is one click because the user is
looking at the table; **Download all** is the one that leaves the building, so it says what it
contains first.

### Merge — S09

| ID | Component | Purpose | States |
|---|---|---|---|
| D31 | **`MergePicker`** | The dialog: schema groups, selection, the check | `empty` · `compatible` · `incompatible` · `merging` · `merged` · `failed` |
| D32 | **`MergeConflict`** | Names the table, the field and the disagreement | Rendered **on the offending `SchemaCard`**, not only in a summary |

**`MergeConflict` goes on the card**, not just at the bottom of the dialog. The user needs to see
*which* selection is the problem, not only that there is one.

### Insights — S10 (P1)

| ID | Component | Purpose | States |
|---|---|---|---|
| D33 | **`InsightCard`** | A chart, one sentence, and a link to the rows behind it | `rendered` — there is no other state |
| D34 | **`InsightList`** | The set of findings | `working` · `findings` · `nothing-to-report` · `not-enough-data` · `failed` |

**`InsightCard` refuses to render without row citations.** The rule that a finding must point at its
rows is enforced in the component, not in a prompt — a prompt can be ignored by a model, a component
cannot.

### Review — S11 (P2)

| ID | Component | Purpose | States |
|---|---|---|---|
| D35 | **`ReviewCard`** | One marked cell: value, reason, evidence, actions | `showing` · `correcting` · `drawing` · `saving` · `saved` |
| D36 | **`ReviewQueue`** | The loop, the progress, the keyboard handling | `active` · `empty` · `done` |

`ReviewCard` reuses `MarkedCellReason` (D18) rather than defining its own copy — the reason a cell
is amber is the same sentence whether you meet it in the table or in the queue.

### Cross-cutting

| ID | Component | Purpose | Notes |
|---|---|---|---|
| D37 | **`FailureMessage`** | **Turns a failure class into a sentence and a next step** | The single place a failure becomes text |
| D38 | **`ConnectionStatus`** | Live updates lost, reconnecting, offline | Global |
| D39 | **`WakingUpState`** | The cold-start pause, named (P1) | Wraps `LoadingState` |

**`FailureMessage` is the one to get right.** Every failure class maps to its copy in exactly one
component. That's what makes "no raw error string ever reaches the user" a structural property
rather than a thing everyone has to remember. If a screen renders `error.message` directly, that's
a bug regardless of how good the message happens to look.

## The four components that carry the product

If these four are right, the rest is assembly.

| Component | Why |
|---|---|
| **`DataCell`** | Four states, used in every table and in review. Get its states wrong and the honesty of the whole product goes with it |
| **`EvidencePanel` + `EvidenceView`** | One interface, five views. A new format means a new view and nothing else changes |
| **`SchemaEditor`** | The panel, the all-files view and the merge picker's cards all render the same shape. Three screens, one truth |
| **`FailureMessage`** | The single place a failure class becomes text |

And two that make rules structural rather than remembered: **`LoadingState`** (no wordless spinner
can be written) and **`GatedButton`** (no unexplained disabled control can be written).

---

## Naming

- **PascalCase**, file named for the component: `DataCell.tsx`
- **No `Quarry` prefix.** The folder already says it
- **No abbreviations.** `EvidencePanel`, never `EvPanel`
- **Say the thing, not the shape.** `PausedBanner`, not `YellowBox`
- Domain components are named for what they *mean*, not where they sit — `DataCell` works in the
  table and in review because it isn't called `TableCell`; `FileRow` works on S02 and S04 because
  it isn't called `UploadRow`

## Do not create these

Common instincts that would break the system.

| Don't | Use instead |
|---|---|
| A second badge or pill | `StatusBadge` with a new variant |
| A bare spinner anywhere | `LoadingState` — it requires a label |
| A disabled `button` with no reason | `GatedButton` — it requires one |
| A separate row component for S04 | `FileRow` with different trailing controls |
| A rename or delete control on a schema field | Nothing. The operation doesn't exist |
| A custom modal | `dialog`, or `sheet` on small screens |
| A toast for an error | `ErrorState` or `FailureMessage` — errors persist, toasts don't |
| A one-off cell renderer | `DataCell` with a new state |
| Rendering `error.message` directly | `FailureMessage` |
| A second table, including for merged results | `DataTable` with different columns |
| A bespoke evidence layout for a new format | A new `EvidenceView` case |
| An insight card without row citations | Nothing. It isn't rendered |
| Your own colour values | The tokens in [`ui-design-spec.md`](ui-design-spec.md) |

## Adding to this inventory

When a genuinely new component is needed:

1. Confirm nothing above covers it, including as a variant
2. Confirm it's earned its place — a third occurrence, or it's clearly domain-shaped
3. Place it in the right layer, and check it only depends downward
4. Name it for meaning
5. **Add it to this file in the same change as the code.** An inventory that lags the codebase is
   worse than none, because it gets trusted and it's wrong

## Build order

Roughly the order these become necessary, which is also roughly the safest order to build them.

```
1. Primitives + StatusBadge, LoadingState, GatedButton,
   EmptyState, ErrorState, PageHeader, SplitPane
2. DropZone, FileRow, FileList                            → uploading works
3. SchemaEditor, SchemaFieldRow, FieldTypeSelect,
   AddFieldControl, SchemaCard                            → S03 works
4. ApplyToAllControl, SchemaGroupList, ConvertBar         → S02 is complete
5. StatusSentence, PausedBanner                           → S04 works
6. DataTable, DataCell, MarkedCellReason, BatchCard       → S06 and S01 work
7. EvidencePanel, EvidenceView, EvidencePageView,
   HighlightBox, EvidenceUnavailable                      → the product works
8. DownloadFileButton, DownloadAllDialog                  → data can leave
9. MergePicker, MergeConflict                             → S09 works
10. FailureMessage everywhere it belongs                  → P0 complete
11. InsightCard, InsightList                              → P1 begins
12. ReviewCard, ReviewQueue, KeyHint                      → P2
```

Step 7 is the one that must not be deferred. Everything before it is a table, and a table isn't the
product.

Step 4 is the one most likely to be underestimated. `ApplyToAllControl` looks like a button and is
actually the difference between correcting one schema and correcting forty.
