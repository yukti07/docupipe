# Quarry infrastructure

Everything in GCP, in one root module. Region is `asia-south1`.

```bash
cp terraform.tfvars.example terraform.tfvars   # fill in, no secrets
terraform init
terraform fmt -check
terraform validate
terraform plan          # a human reads this
terraform apply
```

The database password and the cookie signing key are **generated by Terraform
and written straight to Secret Manager**. Nobody types them, nobody pastes
them into a chat, and they never appear in an output.

## What gets created

```
GCS bucket (+ CORS)          Artifact Registry
Cloud SQL Postgres 16        Cloud Run  ×2   inspect-worker, convert-worker
  └─ database, app user      Cloud Scheduler → /internal/sweep
  └─ password in Secret Mgr  Service accounts ×5
Pub/Sub  ×2 topics           Workload Identity Federation (Vercel OIDC)
  └─ ×2 push subscriptions   Monitoring alert policies ×4
  └─ ×2 dead-letter topics
  └─ ×2 DLQ pull subs
```

## After `apply`

```bash
terraform output vercel_env    # paste into Vercel's environment variables
```

Then build and deploy the worker image, **twice, from the same image**:

```bash
REPO=$(terraform output -raw worker_image_repository)
gcloud builds submit ../../packages/worker --tag "$REPO:$(git rev-parse --short HEAD)"

gcloud run deploy quarry-dev-inspect-worker --image "$REPO@sha256:<digest>" --region asia-south1
gcloud run deploy quarry-dev-convert-worker --image "$REPO@sha256:<digest>" --region asia-south1

terraform plan     # MUST be empty — see below
```

**Deploy by digest, not by tag.** A tag is a moving target and makes a
rollback ambiguous. Rollback is
`gcloud run services update-traffic --to-revisions=...`, never a
`terraform apply`.

## Five things that will otherwise cost you an afternoon

**Terraform does not own the image.** It creates the services with a
placeholder and `ignore_changes` on `template[0].containers[0].image`,
`client` and `client_version`. If `terraform plan` is not empty after a
pipeline deploy, that block is wrong and the next `apply` will revert
production.

**Signed URLs need impersonation and a self-binding.** There is no private key
anywhere, so V4 signing falls back to IAM `signBlob` — which needs to know
whose identity to sign as. That comes from the credential's `client_email`,
and a *direct-access* external-account credential does not have one. The
credential config must include `service_account_impersonation_url`, and the
service account needs `roles/iam.serviceAccountTokenCreator` **on itself**.
Both are in `workload-identity.tf`; the failures are
`Cannot sign data without 'client_email'` and
`Permission 'iam.serviceAccounts.signBlob' denied`.

**Do not pin `environment` in the WIF attribute condition.** Preview
deployments carry `environment: "preview"` and would build and deploy
perfectly and then 500 at runtime.

**CORS is bucket metadata, and `curl` will not catch a mistake.** GCS answers
the browser's preflight from the bucket, not from the signed URL. Test the
upload *from a browser*. And GCS matches origins as exact strings or `*` —
`https://*.vercel.app` does nothing, so previews need `*`. That is fine: the
signed URL is the security boundary, not CORS.

**Dead-lettering needs two grants to the Pub/Sub service agent.** Miss either
and the policy is configured and silently does nothing — which looks exactly
like it working, right up until a poison message cycles forever.

## Costs

Cloud SQL is the only thing that does not scale to zero. `db-f1-micro` is the
cheapest instance that exists and is still a standing monthly charge. Cloud
Run, Pub/Sub, Scheduler and GCS at this volume are effectively free.
