# web — Quarry

Next.js App Router app: the UI **and** the API (D15, D18). Route handlers under
`src/app/api/` are the backend. The Python worker (`packages/worker`) is a separate
runtime reached by `POST {WORKER_URL}/drain` (D25); the two meet only in Postgres.

```bash
cp .env.example .env.local
npm install
npm run dev     # http://localhost:3000
npm run build
npm run lint
```

## Looking at the UI without a backend

```bash
npm run dev:fixtures   # NEXT_PUBLIC_FIXTURES=1
```

The whole app on fixtures: no Postgres, no worker, no bucket. `src/lib/api/index.ts`
swaps `LiveApi` for `FixtureSeven`, and nothing else in the app knows — every screen
imports `api` and none of them import either side directly.

It is a state machine rather than a canned reply, so the screens move: shapes come
back over a few polls and Convert gates on them, uploads walk their progress bars,
tables finish one at a time. Drop files and the rows that come back are the rows you
dropped — one in seven settles without a shape and one in nine holds two tables, so
the "won't convert" panel and the tabbed schema panel are both reachable.

Open a batch link cold instead — any `/b/<anything>`, with nothing dropped — and the
canned 43-file payload in `fixtures/api/schema-poll.json` stands in, which is the
dense end of the screen. Press **Review schemas** to see it: the schema list is
normally gated on this browser's own upload finishing, and a cold visit has no
upload of its own to finish.

The one behaviour that is not the real one is the cadence: the result poll's
two-minute opening wait is zero here (`state/result.tsx`), because two minutes of
spinner is two minutes of a screen nobody can look at.

Query types are generated by introspecting the live database — Alembic in
`packages/db` owns the schema, never this package (D22).
